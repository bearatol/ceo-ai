# 五个技能, 一位理发师, 几个可疑的点子

**以下所有场景均为虚构教学示例.** 每段可以独立阅读, 用来展示工作方式, 并非运行记录, 实测成果, 背书或保证. 故事中的扫描, 观察和测试也都是虚构的.

## CEO

### “先让它闪闪发光，用户以后再说。”

**虚构教学示例。** 以下对话展示一种工作方式，不是真实客户案例、实测成果，也不是对 CEO AI 行为的保证。

**客户：** 我有一个十亿美元的点子：预约应用、社交平台、交易市场，再加上 AI。所有地方都要闪闪发光！

**CEO：** 很有雄心。选特效之前，先确认：我们要解决谁的问题？什么才算成功？

**客户：** 我的理发师总在聊天记录里漏掉预约。但我们必须有全球视野。

**CEO：** 先了解客户如何预约、预约在哪一步丢失。第一个假设可以很小：一位理发师、可选时段、提交预约、收到确认。全球特效先在门外等一下。

**客户：** 好吧。把 API 密钥直接放到网页里，配置方便。也别搞登录，多一步就少一个客户。

**CEO：** 公开的密钥会变成别人花钱、你买单。密钥应留在服务端的秘密管理系统中，只授予必要权限；泄露后应撤销或轮换。我们可以简化预约流程，同时保护密钥和客户记录。

**客户：** 修改网址里的预约编号就能改预约，多直观！

**CEO：** 改别人的发型也很直观。服务器必须检查对每条预约的访问权限，猜到编号不能等于获得授权。测试要覆盖访问他人预约的尝试。具体访问方式应根据数据和流程选择。

**客户：** 用户访谈就省了吧。我也是用户，而且已经说服了自己。

**CEO：** 有了第一条意见，但样本还小。先观察几次真实预约，再用简单原型验证。发现用户卡住时，改草图比重写应用便宜。

**客户：** 宣传页写：“全球最安全的预约系统，保证收入翻倍。”

**CEO：** 这两个承诺都没有证据。先说清实际功能：选择时段并收到确认。然后做一次预算封顶的小规模推广，记录完成预约和中途退出的情况。

**客户：** 那我的颠覆式创新呢？

**CEO：** 也许就是客户终于顺利约上了。先测清现状，再宣布颠覆。

**客户：** 一位理发师、一个原型、访问检查、私密密钥，再做小规模推广测试。确认按钮总能闪一下吧？

**CEO：** 只要仍然清楚、好用。我也曾把动画误当成战略。

**在这个虚构故事中，经过原型迭代和测试之后：**

**客户：** 预约能用了！测试确认无法访问别人的预约，密钥没有公开，宣传也终于把产品说清楚了。

**CEO：** 有了一个实用的初版。随着产品发展，还要继续验证假设。

**虚构结局：** 一个聚焦具体需求、可以工作的预约产品。这不是真实测试成果，也不是安全保证。

## Writer

### "写得像人说话. 但一定要有协同效应."

**客户:** 给老客户写一条理发预约公告. 像我说话, 但要显得专业. 保留"协同效应", 这个词是我花钱上课学来的.

**Writer:** 先给我已经实现的功能和原稿. 事实从笔记里找, 培训课暂时只负责提供收据.

**客户:** 一位理发师, 可选时间, 预约确认, 到店付款. 原稿是:"本方案通过客户与可用时段的无缝协同, 实现预约确认及到店结算."

**Writer:** 改后:"现在可以在线预约理发了. 选择空闲时间, 收到预约确认, 到店后付款."

**客户:** 明白了. 再加一句客户已经赞不绝口?

**Writer:** 需要有反馈证据. 笔记里没有. 改稿保留了预约步骤和付款方式, 没有补上一条虚构好评.

**客户:** 好. 保留"理发". 我不说"形象焕新体验", 除非镜子按字收费.

**Writer:** 保留了. 我还检查了"确认"没有变成"即时确认". 多加两个字, 就会承诺笔记里没有说明的速度.

**客户:** 永远记住这个偏好. 等等, 只用于这条公告. 那协同效应怎么办?

**Writer:** 记忆保持关闭, 这次修改只在当前对话中使用. "协同效应"可以留给等候区的填字游戏. 公告已备好供你审阅, 尚未发布.

## Security

### "检查预约应用。直接测线上可以吗？"

*虚构演示；没有访问任何系统，也没有实际执行测试。*

**客户:** 检查预约应用的安全性。直接测线上可以吗？希望我们先发现漏洞，而不是客户。

**Security:** 哪些目标归你所有或已获准测试，范围是什么？可以先查看获准的代码和配置。主动测试需要具体方案和知情同意；宿主权限与政策仍然有效。

**客户:** https://booking-staging.example.invalid 属于我们，范围仅限 /api/bookings/synthetic-17。审查预约处理代码和访问控制配置。我们有两个测试账号和虚构预约。生产、支付与第三方系统都不在范围内。暂时不要发主动请求。

**Security:** 在虚构代码审查中，处理程序似乎只检查登录，没有检查预约归属。一个账号可能读到另一个账号的预约。这是代码支持的假设，还不能证明部署后的 API 会这样响应。

**客户:** 怎么验证，才不会把预约变成事故？

**Security:** 建议向获准的 staging 预约端点发送两次只读 GET：第一次用虚构预约的所有者账号，第二次用另一个测试账号读取同一预约。目的是验证归属边界。最多两次请求，逐次发送，60 秒内结束，每次超时 5 秒，禁用重定向，不重试、不主动修改预约数据。读取也可能留下日志或暴露数据。更安全的选择是保留代码审查假设，不主动验证。遇到真实数据、不稳定、意外跳转或范围变化立即停止。仅记录状态和虚构预约标记，不在报告保存凭据，之后丢弃本地测试客户端，不发送额外请求。读取仍可能改变日志或会话元数据；若无法完成预先约定的清理，就停止并说明。是否批准这个方案？

**客户:** 在这个虚构故事中，我批准这项 staging 测试：仅用那两个测试账号，最多两次请求、60 秒，遵守上述停止和本地客户端清理规则，不访问生产。

**Security:** 虚构结果：第二个账号也收到虚构预约标记。取得最小证据后立即停止。报告说明端点、条件、观察到的响应及影响，不保存令牌或无关数据。应在服务端实施归属检查，再按获准的复测方案确认所有者可访问，另一个账号被拒绝。

**客户:** 修完后就能给整个应用盖“安全”章了吗？

**Security:** 不能。此例仅覆盖一条访问控制路径。移动客户端、基础设施、AI 集成和其他端点未测试。无法执行的检查仍未验证。报告区分证据与假设。目标或风险变化需要新的同意；原授权仅在范围和风险不变时继续适用。

## Debugger

### "按钮坏了. 把公司重写一遍吧."

**客户:** 理发预约按钮没反应. 换框架, 换数据库, 顺便换理发师?

**Debugger:** 先做最小复现: 选择时间, 点击"预约", 预期出现确认. 在故事的测试环境里, 问题复现了. 换剪刀之前先追踪点击.

**客户:** 肯定是服务器. 看起来就像它干的.

**Debugger:** 请求到了就看响应, 没发出就查客户端. 故事中的追踪显示没有发出请求. 点击处理函数运行后退出, 因为它读取 `selectedSlot`, 选时控件却写入 `slotId`.

**客户:** 一个预约两个名字, 真高级. 按商定范围修好它.

**Debugger:** 先让针对性测试在选时后失败. 再把读取字段改为 `slotId`. 在虚构检查中, 同一复现步骤和测试通过. 没选时间时仍会提示先选择时间.

**单独一幕: 重构.**

**客户:** 现在合并两个确认信息生成函数, 保留原有输出. 顺便塞个会员计划进去?

**Debugger:** 会员计划另算. 这次先记录两个函数的文本, 错误和发送次数, 再提取共用格式逻辑, 每一步都与原有行为比较.

**客户:** 结果呢?

**Debugger:** 故事中的比较显示, 确认文本, 错误和只发送一次的行为一致. 重复的格式代码去掉了. 检查只覆盖这些路径, 不代表所有输入都验证过. 理发师保住了剪刀, 也保住了框架.

## User Review

### "按钮很明显. 是我亲自想的."

**客户:** 看看这个理发预约页面. 按钮写着"激活你的蜕变". 一看就知道是预约.

**User Review:** 目标是预约周二晚上的理发. 我根据提供的截图, 分别采用疲惫的首次到访客户和有经验的沙龙前台两个视角. 前台也累了, 而且第一次使用这个应用. 这是模拟审查.

**客户:** 新手可以学我们的术语. 页脚有词汇表.

**User Review:** 新手视角: 可见的空闲时段让人有理由继续, 但按钮没说要做什么. 疲惫的读者可能以为"蜕变"会打开护发产品推荐, 因而犹豫. 这是根据文案提出的假设, 不是观察到的离开行为.

**客户:** 前台肯定懂. 天天都在排预约.

**User Review:** 专业视角: 时间有用, 但截图没有服务时长. 对方可能因为无法判断是否排得下而暂停. 行业经验不会让隐藏字段自动显现.

**客户:** 那把按钮放大? 它已经快占满整个周二了.

**User Review:** 先改成"预约周二 18:00". 旁边列出服务, 时长和价格. 字多了一点, 但能帮助决定. 预约后要显示确认和修改入口. 截图无法验证这些交互.

**客户:** 如果他们预约完马上走呢? 停留时长会很难看.

**User Review:** 那可能正是成功. 两个视角的目标都是确认预约后自由离开. 接下来在获准的测试环境中, 用真实预约尝试验证文案和缺失信息. 目前只有修改建议, 没有实测用户结果.
